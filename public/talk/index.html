THE MOTIVE

Designed around vs. designed for

Designed around

  • Visual design comes first
  • Screen reader support patched in at the end
  • aria-label sprinkled on top to make the audit pass
  • Tested once before launch, if at all

Designed for

  • The text is the game
  • Visuals are an optional overlay
  • Every clue lives in the DOM
  • Tested with VoiceOver, NVDA, and the keyboard while building

THE ENGINE

The engine is just a function

// engine/reducer.ts
export function gameReducer(
  state: GameState, action: GameAction
): GameState {
  switch (action.type) {
    case "MOVE_TO_ROOM":
      return { ...state, currentRoomId: action.roomId, … };
    case "EXAMINE_OBJECT":
      return { ...state, phase: "examining",
               examinedObjectId: action.objectId };
    // ADVANCE_DIALOGUE, START_CONFRONTATION…
  }
}

Pure TypeScript. No React, no DOM.

State and action in, new state out. Every move, clue and line of dialogue is just an action.

Easy to test, no browser needed.

Typewriter text, one announcement

  aria-atomic="true">

</div>

Instant

The default, and always on in Screen Reader Mode. One live region, the full text lands at once.

Typewriter

Visual Mode only. The text types itself out letter by letter, every 30ms, like an old adventure game.

The solution

The screen reader hears the full text once, from a visually hidden live region. The animated copy is aria-hidden.

THE ENGINE

When content swaps, focus has to move

const narrationRef = useRef<HTMLDivElement>(null);

useEffect(() => {
  narrationRef.current?.focus();
}, [state.currentRoomId, state.examinedObjectId, state.phase]);

<section id="narration" tabIndex={-1} ref={narrationRef}>

Without it

You press “Go to the hallway”. That button disappears. Focus falls back to the body. You’re lost.

With it

Focus lands on the new room’s narration. Tab takes you straight to the actions.

THE ENGINE

Route changes need focus too

Full page load

Focus starts at the top of the new page and the screen reader announces its title. You know where you are.

Client-side routing

The URL and the content change, but focus stays on a link that may not exist anymore. The screen reader says nothing.

// runs on every route change
useEffect(() => {
  const h1 = document.querySelector("main h1");
  h1?.focus();
}, [pathname]);

<h1 tabIndex={-1}>How to play</h1>

The solution

After every route change, move focus to the new page’s h1. The screen reader reads it, so you know the page changed and where you are.

tabIndex -1 lets the h1 take focus without adding it to the Tab order.

THE ENGINE

Two display modes, one accessibility tree

Screen Reader Mode (default)

A black screen with only the narration. Every control is still there, just visually hidden.

Visual Mode

Pixel art layout, typewriter text, pixel or Inter font. Same DOM, same clues.

.display-screenreader button,
.display-screenreader [data-role="ui"] {
  position: absolute;
  width: 1px; height: 1px;
  clip-path: inset(50%);
  overflow: hidden;
}

Visually hidden is not display: none.

display: none removes it from the accessibility tree too.

THE ENGINE

Speak the right language

// layout.tsx, server
const locale = await getLocale();

<html lang={locale}>

// SetHtmlLang.tsx, client
useEffect(() => {
  document.documentElement.lang = locale;
}, [locale]);

Why it matters

lang picks the screen reader’s voice and pronunciation. Spanish read by an English voice is gibberish.

On the server

The root layout reads the locale with getLocale(), so the HTML has the right lang from the first byte.

On the client

A small effect keeps it in sync when you switch language mid-session, without a full reload.
