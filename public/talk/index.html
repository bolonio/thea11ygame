THE MOTIVE

Designed around vs. designed for

Designed around

  • Visual design comes first
  • Screen reader support patched in at the end
  • aria-label sprinkled on top to make the audit pass
  • Tested once before launch, if at all

Designed for

  • The text is the game
  • Visuals are an optional overlay
  • Every clue lives in the DOM
  • Tested with VoiceOver, NVDA, and the keyboard while building

thea11ygame.com

Speaker notes

Most of what we ship is designed around the screen reader. We build the visual thing, then near the end someone runs an audit, and we add aria-labels until the tool goes green. It technically works, but nobody designed that experience. I wanted to flip it. What happens if the screen reader is the primary platform and the visuals are the add-on? That flip changes every decision: the content model, the components, how you test.

in the text.

Speaker notes

This is the one rule I wrote in the design spec before writing any code, and everything else follows from it. Visual mode is a supplementary layer, never a gameplay advantage. If a sighted player could spot something on screen that a screen reader user can’t hear, that’s a bug. Think about how often the opposite is true in our products: the chart with no data table, the icon with no label, the red border that’s the only hint a field is wrong.

thea11ygame.com

Speaker notes

Quick screen reader 101, because I bet many of you have never turned one on. A screen reader doesn’t look at your screen. The browser turns your HTML into an accessibility tree, and the screen reader walks that tree and turns it into speech or braille. For each element it gets a name, a role and a state. So a button in the game is announced as “Examine The heavy footsteps, button”. And that name is everything. Imagine the same button called “Click here” or “Next”. Sighted users get the context from the layout around it, but a screen reader user often hears the button on its own, for example while tabbing or from a list of all the buttons on the page. “Click here, button” tells you nothing about what will happen. “Examine The heavy footsteps, button” tells you exactly what you’re about to do. So write accessible names that describe the action, and make sense out of context. Your CSS, your layout, your beautiful gradient: invisible. A div with a click handler: also invisible, because it has no role. And it’s linear. The user hears one thing at a time, so order and structure are everything.

Speaker notes

Here’s the full path from a data file to the screen reader. One: each episode is plain data, one file per language, with rooms, characters, clues, the confrontation and the endings. When the file is imported, it calls registerEpisode. Two: the registry is just a Map, keyed by episode id and language, so earwitness:en and earwitness:es are two separate entries, and getEpisode picks the right one for the current locale. Three: GameContext holds the game state with useReducer and saves it to localStorage, with one save per episode and language, so playing in Spanish never overwrites your English progress. Four: the engine is a pure TypeScript reducer. It takes the state and an action like MOVE_TO_ROOM, EXAMINE_OBJECT or ADVANCE_DIALOGUE, and returns the new state. No React, no DOM, easy to test. And five: GameShell looks at state.phase and renders exactly one view: the intro, the room with its actions, a dialogue, the confrontation or the ending. Every one of those views is where the accessibility lives: headings, live regions and focus. The engine never has to know.

THE ENGINE

The engine is just a function

// engine/reducer.ts
export function gameReducer(
  state: GameState, action: GameAction
): GameState {
  switch (action.type) {
    case "MOVE_TO_ROOM":
      return { ...state, currentRoomId: action.roomId, … };
    case "EXAMINE_OBJECT":
      return { ...state, phase: "examining",
               examinedObjectId: action.objectId };
    // ADVANCE_DIALOGUE, START_CONFRONTATION…
  }
}

Pure TypeScript. No React, no DOM.

State and action in, new state out. Every move, clue and line of dialogue is just an action.

Easy to test, no browser needed.

thea11ygame.com

Speaker notes

The heart of the game is one function. The engine is a pure TypeScript reducer: it takes the current state and an action, like MOVE_TO_ROOM, EXAMINE_OBJECT or ADVANCE_DIALOGUE, and returns the new state. Moving to a room just sets the current room. Examining an object switches the phase and remembers which object you’re looking at. That’s it. There’s no React in here, no DOM, no fetch, no timers, nothing that needs a browser. Which means it’s easy to test: give it a state and an action, check what comes out. And it keeps the accessibility work where it belongs, in the views that render this state.

Speaker notes

Once we have the episode, GameContext takes over. It looks for a saved game for this episode and this language in localStorage. If there is one, you continue where you left off; if not, it creates a fresh initial state in the starting room. Instant

The default, and always on in Screen Reader Mode. One live region, the full text lands at once.

Typewriter

The solution

The screen reader hears the full text once, from a visually hidden live region. The animated copy is aria-hidden.

thea11ygame.com

Speaker notes

Let’s talk about narration speed. The game has two text speeds. Instant is the default, and in Screen Reader Mode it’s forced: the full text lands in a polite, atomic live region and gets announced once. In Visual Mode you can switch to Typewriter, where the text types itself out every 30 milliseconds, like an old adventure game. Plenty of low-vision players use Visual Mode with a screen reader on, so the typewriter has to work for both. If the animated text were the live region, it would change every 30ms, and an atomic region would re-read the whole sentence on every tick. So the two jobs are split. The full text goes once into a visually hidden live region, that’s what the screen reader hears. The animated copy is aria-hidden, that’s what the eyes see. Same content, two channels, each doing one thing. Lesson: animations aren’t only a motion problem, they can be a screen reader problem too. Separate what you show from what you announce.

THE ENGINE

When content swaps, focus has to move

const narrationRef = useRef<HTMLDivElement>(null);

  narrationRef.current?.focus();
}, [state.currentRoomId, state.examinedObjectId, state.phase]);

<section id="narration" tabIndex={-1} ref={narrationRef}>

Without it

You press “Go to the hallway”. That button disappears. Focus falls back to the body. You’re lost.

With it

Focus lands on the new room’s narration. Tab takes you straight to the actions.

thea11ygame.com

Speaker notes

This is the pattern I’d tattoo on every SPA developer. When you click a button and the content around it is replaced, the button you were focused on no longer exists. The browser drops focus to the body, and a screen reader user is suddenly at the top of the page, or hears nothing at all. In the game, whenever the room, the examined object or the phase changes, I move focus to the narration section. tabIndex minus one makes it focusable by script without adding it to the Tab order. Sighted keyboard users benefit too: their next Tab goes to the first action, not back to the top.

THE ENGINE

Route changes need focus too

Full page load

Focus starts at the top of the new page and the screen reader announces its title. You know where you are.

Client-side routing

The URL and the content change, but focus stays on a link that may not exist anymore. The screen reader says nothing.

// runs on every route change
useEffect(() => {
  const h1 = document.querySelector("main h1");
  h1?.focus();
}, [pathname]);

<h1 tabIndex={-1}>How to play</h1>

The solution

After every route change, move focus to the new page’s h1. The screen reader reads it, so you know the page changed and where you are.

tabIndex -1 lets the h1 take focus without adding it to the Tab order.

thea11ygame.com

Speaker notes

Same problem as the last slide, one level up: whole pages instead of parts of a page. On a classic website, every click on a link loads a new page. The browser resets focus to the top and the screen reader announces the new title, so you always know where you landed. Single page apps like Next.js don’t reload. The URL changes, the content changes, but focus stays on the link you just clicked, which might not even exist anymore. For a screen reader user, nothing happened. Silence. The solution in the game is a tiny component in the layout. Every time the pathname changes, it finds the h1 inside main and moves focus to it. The screen reader reads the heading, “How to play”, and now you know the page changed and where you are. The h1 has tabIndex minus one, so it can receive focus from code without becoming a stop when you press Tab. The game screen itself skips this, because it already moves focus to the narration. If your app uses client-side routing, check this today: click a link with a screen reader on and listen.

THE ENGINE

Speak the right language

// layout.tsx, server
const locale = await getLocale();

<html lang={locale}>

// SetHtmlLang.tsx, client
useEffect(() => {
  document.documentElement.lang = locale;
}, [locale]);

Why it matters

lang picks the screen reader’s voice and pronunciation. Spanish read by an English voice is gibberish.

On the server

The root layout reads the locale with getLocale(), so the HTML has the right lang from the first byte.

On the client

A small effect keeps it in sync when you switch language mid-session, without a full reload.

thea11ygame.com

Speaker notes

The last pattern is one attribute, and it’s one of the most forgotten. The lang attribute on html tells the screen reader which voice and pronunciation rules to use. Spanish read with an English voice is close to unusable, and you can’t fix it with CSS or a nicer UI. So in the game it’s set in two places. On the server, the root layout reads the locale with getLocale from next-intl and renders html lang with it, so the very first HTML the screen reader gets is already right. A screen reader starts reading as soon as the page arrives, it doesn’t wait for React. And on the client, a tiny effect called SetHtmlLang updates it whenever you switch language mid-session, because Next.js keeps the root layout between those navigations. If it matters to assistive tech, make it right in the server HTML. On top of that, episodes are registered per locale and saves are keyed per episode and language, so you can play Earwitness in English and in Spanish without one save overwriting the other. Quick demo option: switch the game to /es and let VoiceOver read a line.

Turn on VoiceOver or NVDA and use your own product for ten minutes without looking. You’ll find the first unlabelled icon button in the first minute, I promise. Two: follow the headings. Jump through them with H or the rotor. If they don’t tell the story of the page, that’s your first clue. Three: track the focus. Every time the route changes or content gets swapped, ask where focus went. If the answer is “the body”, you’ve found your victim. Four: listen for silences. Toasts, errors, loading states that nobody announces are witnesses that never talk. Give them a polite live region. Five: check the accent. If lang on html is wrong, the screen reader reads your page with the wrong voice. None of this needs a new library. And if you want to practise the keys first, go play The A11y Game tonight.
